# 数据库设计说明

## 一、项目概述

本项目为《数据库系统设计》课程大作业的高校教室管理系统。系统目标是实现教室资源管理、课程安排、预约申请、审批流程和统计分析。

本项目采用“轻量化数据库设计 + MySQL 实现”的方案，重点在于：

- 数据库设计合理性
- 外键与完整性约束
- 触发器实现业务规则
- 视图与统计查询
- 文档清晰可读

## 二、设计原则

### 2.1 简化设计

课程设计阶段不追求业务完备性，而是优先完成核心功能。因而：

- 不建立 `Role` 表
- 不建立 `Building` 表
- 不建立 `Department` 表
- 不建立 `Schedule_Adjustment` 表
- 不考虑复杂的调课、补课、教室变更等高级场景

### 2.2 统一用户模型

所有用户信息存储在 `User` 表。用户类型采用枚举字段 `role` 表示，包含：

- `ADMIN`
- `TEACHER`
- `STUDENT`

### 2.3 节次模式

系统统一采用节次表示时间，不使用具体时刻作为主业务时间维度。教室预约与课程排课均使用：

- `start_period`
- `end_period`

节次范围为 `1` 到 `13`。

### 2.4 本地数据库协作方案

组员协作采用“代码共享、数据库本地搭建”方案：

- 共享代码、SQL 脚本、文档
- 各自本地搭建 MySQL 数据库
- 不上传 `classrooms.db` 或任何真实数据库文件
- 数据库连接信息写入 `.env`，且 `.env` 必须被 `.gitignore` 忽略

## 三、核心表结构

系统共设计 8 张核心表：

1. `User`
2. `Classroom`
3. `Device`
4. `Classroom_Device`
5. `Course`
6. `Schedule`
7. `Reservation`
8. `Reservation_Audit`

每张表的目的如下：

- `User`：存储管理员、教师、学生的账号与基本信息
- `Classroom`：存储教室基本信息与状态
- `Device`：存储校园设备类型信息
- `Classroom_Device`：存储教室与设备的多对多关系与数量
- `Course`：存储课程基本信息与任课教师
- `Schedule`：存储固定课程排课信息
- `Reservation`：存储教室预约申请记录
- `Reservation_Audit`：存储管理员审核记录

## 四、实体关系

### 4.1 用户与课程

- `User`（教师）1 → N `Course`

### 4.2 用户与预约

- `User` 1 → N `Reservation`

### 4.3 管理员与审核记录

- `User`（管理员）1 → N `Reservation_Audit`

### 4.4 教室与设备

- `Classroom` N ↔ N `Device`
- 通过 `Classroom_Device` 关联

### 4.5 课程与排课

- `Course` 1 → N `Schedule`

### 4.6 教室与排课

- `Classroom` 1 → N `Schedule`

### 4.7 教室与预约

- `Classroom` 1 → N `Reservation`

### 4.8 预约与审核

- `Reservation` 1 → N `Reservation_Audit`

## 五、完整性约束

### 5.1 主键约束

每张表均设置主键保证唯一性。

### 5.2 外键约束

- `Course.teacher_id` → `User.user_id`
- `Schedule.course_id` → `Course.course_id`
- `Schedule.classroom_id` → `Classroom.classroom_id`
- `Reservation.user_id` → `User.user_id`
- `Reservation.classroom_id` → `Classroom.classroom_id`
- `Reservation_Audit.reservation_id` → `Reservation.reservation_id`
- `Reservation_Audit.admin_id` → `User.user_id`

### 5.3 唯一约束

- `Classroom` 的 `(building, room_number)` 必须唯一。

### 5.4 CHECK 约束

- `capacity > 0`
- `quantity > 0`
- `start_period BETWEEN 1 AND 13`
- `end_period BETWEEN 1 AND 13`
- `start_period <= end_period`
- `start_week <= end_week`

## 六、触发器设计

### 6.1 预约冲突检测触发器

- 触发时机：`BEFORE INSERT ON Reservation`
- 功能：防止同一教室在同一日期、同一节次范围内被重复预约或与课程安排冲突。
- 检查对象：
  - 待审核预约记录
  - 已通过预约记录
  - 课表排课记录
- 关键条件：同教室、同日期/同星期、节次重叠。

### 6.2 审核状态同步触发器

- 触发时机：`AFTER INSERT ON Reservation_Audit`
- 功能：根据审核结果自动更新 `Reservation.status`。
- 规则：
  - `APPROVED` → `Reservation.status = APPROVED`
  - `REJECTED` → `Reservation.status = REJECTED`

## 七、视图设计

### 7.1 `View_Reservation_Detail`

- 关联 `Reservation`、`User`、`Classroom`
- 用于展示预约详情和审批结果

### 7.2 `View_Course_Schedule`

- 关联 `Schedule`、`Course`、`User`、`Classroom`
- 用于展示教师课程安排与教室使用情况

### 7.3 `View_Classroom_Usage`

- 用于统计教室利用率、预约检索与资源分析

## 八、统计分析功能

已在 `sql/queries.sql` 中整理以下常用查询：

1. 教室利用率统计
2. 热门教室统计
3. 教师课程数量统计
4. 月度预约次数统计
5. 空闲教室查询
6. 待审核预约查询
7. 用户预约记录查询

## 九、开发顺序建议

### 第一阶段：数据库基础结构

在 `sql/create_tables.sql` 中创建基础数据表，按照依赖顺序建立：

1. `User`
2. `Classroom`
3. `Device`
4. `Course`
5. `Classroom_Device`
6. `Schedule`
7. `Reservation`
8. `Reservation_Audit`

- 教室、设备
- 课程、排课
- 预约申请、审核记录

### 第三阶段：实现触发器

### 第四阶段：实现视图

### 第五阶段：实现统计查询

在 `sql/queries.sql` 中补充常用统计查询语句。

## 十、协作说明

### 10.1 文档使用方式

组员请以 `docs/数据库设计说明.md` 和 `docs/数据字典.md` 为主要设计参考，不需要查看 `design.md` 和 `plan.md`。

### 10.2 SQL 开发流程

- 所有表结构和约束写入 `sql/create_tables.sql`
- 测试数据写入 `sql/insert_test_data.sql`
- 触发器写入 `sql/triggers.sql`
- 视图写入 `sql/views.sql`
- 常用统计查询写入 `sql/queries.sql`

### 10.3 数据库搭建

各组员本地搭建 MySQL，并执行 `sql/create_tables.sql` 与 `sql/insert_test_data.sql`。

### 10.4 敏感信息处理

- 不提交 `.env`
- 不提交 `classrooms.db`
- 数据库连接配置存入本地 `.env`
